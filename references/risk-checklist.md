# 风险识别清单

> 用途：逐条过一遍，把命中的项转成风险表里的行。**每条都必须写出早期触发信号**——这是风险表里唯一真正有用的列。
> 「可能延期」不是风险，是废话。风险 = 一个能被观测到的信号 + 一个具体的后果 + 一个可执行的应对。

## 一、技术风险

- [ ] 存在需要预研验证的核心难点（算法、性能、精度、兼容性）→ 应对：先写最小 demo，验证失败要能承受
- [ ] 依赖的库/框架处于早期阶段（<1.0 或社区很小）→ 应对：评估源码可维护性，或做抽象层隔离
- [ ] 需要与老系统/老设备对接，接口文档缺失或无维护方 → 应对：抓包逆向 + 预留适配层
- [ ] 性能指标依赖硬件或网络环境（低端机、弱网、大文件）→ 应对：定基线设备，先在基线环境测
- [ ] 数据一致性要求高（订单、库存、计费）→ 应对：明确一致性边界，设计对账与补偿机制
- [ ] 需要跨端一致（小程序/iOS/Android/Web 表现不同）→ 应对：列出差异点，按「最小公共集」设计
- [ ] 技术栈中有团队完全没接触过的部分 → 应对：估入学习成本，或换成熟方案

## 二、依赖风险（最容易被漏掉的一类）

- [ ] 第三方平台政策/审核规则可能变化（应用商店、小程序类目、支付通道）
- [ ] 第三方 API 有配额、限流、涨价、下线风险 → 应对：抽象接口层 + 备份方案
- [ ] 上游供应商交期（硬件打样、模组、认证证书）
- [ ] 关键账号/资质在他人名下（域名、备案、云账号、开发者资质）
- [ ] 依赖某个人的个人经验或私有环境（单点依赖）
- [ ] 开源协议存在传染性（GPL/AGPL）会影响商业闭源

## 三、进度风险

- [ ] 里程碑没有可验证的验收标准 → 无法判断是否真的完成
- [ ] 关键路径上有多项串行工作（设计→开发→联调→审核）
- [ ] 需求在开发过程中可能变更（无变更控制机制）
- [ ] 需要等待外部审核/审批（周期以周或月计，且不可控）
- [ ] 团队同时承接多个项目（上下文切换损耗未计入）
- [ ] 没有为联调、返工、修 bug 预留缓冲（建议每阶段 20%~30%）

## 四、成本风险

- [ ] 云资源按量计费，流量/存储/调用量增长后成本非线性上升
- [ ] LLM/第三方 API 按次计费，日调用量 × 单价需要算过
- [ ] 硬件打样、模具、认证费用（一次性但金额大）
- [ ] 短信/推送/地图等按量服务有免费额度陷阱
- [ ] 人力成本按「实际可用工时」算，不是按自然日

## 五、安全与合规风险

- [ ] 收集个人信息（手机号、位置、身份）→ 需要隐私政策、最小必要原则、加密存储
- [ ] 涉及行业资质（医疗、金融、教育、直播、地图）
- [ ] 设备需要强制认证（CE/FCC/SRRC/CCC，周期以月计）
- [ ] 密钥/证书管理（硬编码密钥、证书过期）
- [ ] 越权访问、未做输入校验、日志泄露敏感信息
- [ ] 数据存储地域限制（跨境传输）

## 六、运维与可维护风险

- [ ] 没有日志与监控，出问题只能靠猜
- [ ] 没有备份与恢复流程
- [ ] 没有回滚方案（发布即不可逆）
- [ ] 配置散落在代码里，改环境要改代码
- [ ] 无文档，接手成本极高
- [ ] 定时任务/后台作业无失败告警

## 七、嵌入式专项风险

- [ ] Flash/RAM 预算未定，后期功能加不进去
- [ ] 功耗预算未定，电池寿命达不到标称
- [ ] 无 OTA 或 OTA 无回滚，量产固件出问题只能召回
- [ ] 硬件版本与固件版本未做兼容矩阵
- [ ] 通信协议未定版本号与扩展机制，后续改协议要全量升级
- [ ] 无产测方案（校准、序列号、出厂检测）
- [ ] 弱网/断网/掉电场景未设计（重连、缓存、幂等）
- [ ] 现场问题无法远程定位（无日志导出、无故障快照）

## 转成风险表的写法

| 要素 | 好例子 | 坏例子 |
|---|---|---|
| 风险 | MQTT 长连接在 4G 弱网下频繁掉线，导致指令丢失 | 网络可能不稳定 |
| 早期信号 | 联调阶段观察到日均重连次数 > 20 次 | （缺失） |
| 影响 | 用户下发指令失败率上升，需人工重试 | 影响体验 |
| 应对 | 应用层心跳 + 指令序号幂等 + 离线队列重发 | 注意网络问题 |
| 回退 | 若重连仍不稳，降级为 HTTP 轮询（延迟可接受） | （缺失） |

**高风险项（概率高×影响大）必须写明是否可回退。不可回退的，唯一正确做法是把它前置到 M0/M1 阶段做验证。**
