# 技术栈选型参考

> 用途：给出「该项目形态下值得考虑的候选组合」，**不是推荐清单**。最终结论必须由项目约束推导，不能直接照抄。
> 版本一律只锁主版本（如 Node 20+），具体小版本需在实施时按官方最新稳定版确认。

## 选型的正确顺序

```
项目约束 → 候选 2~3 套 → 维度对比 → 决策 + 否决理由 → 反过度设计检查
```

反了就是技术堆砌。约束排序模板（按项目实际情况重排）：

1. 团队是否熟悉（个人/小团队项目几乎永远第一）
2. 生态成熟度与文档质量（遇到坑能不能搜到答案）
3. 部署与运维成本（有没有人维护）
4. 性能是否够用（够用即可，不做过度优化）
5. 长期维护性（会不会一年后没人接手）
6. 招聘与替换成本（团队要扩张时才重要）

## 按项目形态的候选组合

### 1. 微信小程序 + 后端

| 层 | 候选 A | 候选 B | 候选 C | 常见否决点 |
|---|---|---|---|---|
| 小程序框架 | 原生小程序 | uni-app (Vue) | Taro (React) | 原生最稳但只能发小程序；跨端框架在原生能力密集时踩坑多 |
| 后端 | Node.js (Express/Koa/Fastify) | Python (FastAPI) | Java (Spring Boot) | 小团队优先选与前端同语言；Spring 生态全但启动与运维重 |
| 数据库 | MySQL/PostgreSQL | SQLite（单机/嵌入式场景） | 云数据库（腾讯云/阿里云） | 并发与数据量极小时上 PG 集群属于过度设计 |
| 实时/推送 | MQTT broker | WebSocket 自建 | 云厂商 IoT 平台 | 设备侧多、需弱网重连时 MQTT 更合适 |
| 部署 | 单台轻量云 + 反向代理 | 容器 + 编排 | Serverless | 无运维经验时，单机 + systemd/pm2 是最省心的起点 |
| 域名证书 | 备案域名 + 免费证书 | — | — | 国内服务器必须备案，周期以周计，需前置 |

**平台硬限制（规划时必须核对，以官方最新文档为准）**：主包体积上限、单包上限、类目资质要求、支付/直播等特殊接口的开通条件、iOS 端无法跳外部支付。

### 2. Web / H5 / 管理后台

| 层 | 候选 | 说明 |
|---|---|---|
| 框架 | React / Vue / Svelte | 选团队熟的；管理后台优先看组件生态而非框架本身 |
| 组件库 | Ant Design / Element Plus / shadcn 类 | 后台表单表格多，组件库成熟度直接决定工期 |
| 构建 | Vite | 已成为默认选择 |
| 状态/请求 | 框架自带 + TanStack Query 类 | 数据请求缓存比全局状态管理更该先解决 |
| 后端 | 同上一节 | 内部工具可用 BaaS/低代码，省掉 60% 工作量 |

### 3. 纯后端 / API 服务

| 关注点 | 决策要点 |
|---|---|
| 语言 | 团队熟的优先；IO 密集选 Node/Go，计算密集选 Go/Rust，数据处理选 Python |
| 数据库 | 先单库。读写分离、分库分表在**验证到瓶颈后**再做 |
| 缓存 | 并发 <1000 时先用进程内缓存；Redis 的引入理由是「跨进程共享」或「持久化队列」，不是「快」 |
| 队列 | 没有真正的异步解耦需求就不要上 MQ；单机定时任务 + 数据库状态机可覆盖多数场景 |
| 部署 | 单机 + 容器即可；K8s 的引入理由是「多环境多副本自动扩缩」，不是「现代化」 |

### 4. 桌面 / 内部工具

| 场景 | 候选 |
|---|---|
| 需要原生性能与系统调用 | C# / WPF、Rust + Tauri、C++ / Qt |
| 快速内部工具 | Electron + Web 技术栈、Python + PySide |
| 硬件交互（串口/网口调试工具） | Python + pyserial/PyQt、C# WinForms、或直接命令行 + 脚本 |

### 5. 嵌入式 / MCU 固件

| 关注点 | 决策要点 |
|---|---|
| 裸机前后台 vs RTOS | 任务少（<5 个并发逻辑）、时序要求松、RAM 紧张 → 裸机；有明显并发/阻塞 IO/多状态机 → RTOS（FreeRTOS/Zephyr/RT-Thread） |
| 通信协议 | 先定帧格式与字段语义，再写业务；预留版本号与扩展位 |
| 无线方案 | BLE / WiFi / 蜂窝（Cat-1 / NB-IoT）按功耗、流量、成本、认证周期选 |
| OTA | 规划阶段就定分区方案与回滚策略，事后补极痛 |
| 量产 | 烧录方式、产测模式、校准参数与序列号存储必须进方案 |

详细清单见 [embedded-adaptation.md](embedded-adaptation.md)。

### 6. AI / LLM 应用

| 关注点 | 决策要点 |
|---|---|
| 模型接入 | 先用官方 API 验证效果，不要提前自建推理 |
| 检索 | 数据量小用关键词 + 向量混合；不要一上来建复杂 RAG 管线 |
| 成本 | 规划阶段就算「单次调用成本 × 日调用量」，这是最容易失控的一项 |
| 兜底 | 必须有超时、降级、限流；模型不可用时业务要能退化运行 |

## 对比表写法

只打符号不给理由的对比表是无效的：

| 维度 | 候选 A | 候选 B |
|---|---|---|
| 团队熟悉度 | ✅ 现役技术栈，无需学习成本 | ⚠️ 需 1~2 周上手，期间交付速度减半 |
| 部署复杂度 | ✅ 单机二进制 | ❌ 需要额外维护运行时与依赖树 |
| 生态 | ⚠️ 社区小，冷门问题需读源码 | ✅ 大量现成方案 |

## 反过度设计检查清单

每引入一个组件，回答「不加它会具体坏在哪」：

- [ ] 缓存：不加，具体哪个查询会慢到不可接受？（给出预估 QPS 与耗时）
- [ ] 消息队列：不加，具体哪个流程会因为同步阻塞出问题？
- [ ] 微服务：不加，单体在哪个维度上真的撑不住？
- [ ] 容器编排：不加，几台机器？谁做运维？
- [ ] 读写分离/分库分表：预估数据量与写入 QPS 是多少？多久会到瓶颈？
- [ ] CDN/对象存储：资源体积与带宽成本算过吗？

答不上来的，就说明现在不需要。
