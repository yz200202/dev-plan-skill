# 嵌入式 / MCU 项目规划专项

> 用途：项目形态涉及 MCU 固件、设备端、硬件联调、量产时，在通用六阶段之外追加以下检查项。
> 核心差异：**嵌入式项目的最大成本不是写代码，而是「验证周期」和「改不动的成本」。** 规划阶段漏掉的东西，量产阶段要用召回级别代价补。

## 一、资源预算（规划阶段就要定量，不能留到实现时再说）

在方案里给出预算表，并明确各项余量。**没有预算表的嵌入式方案等于没做方案。**

| 项目 | 预算值 | 已分配 | 余量 | 说明 |
|---|---|---|---|---|
| Flash (Code) | | | ≥20% | 含 bootloader 与 OTA 双分区 |
| Flash (Data/参数) | | | ≥30% | 校准参数、配置、日志 |
| RAM (静态 + 堆栈) | | | ≥25% | 栈深度需按最坏中断嵌套估 |
| 平均电流 | | | ≥30% | 决定电池寿命，需按占空比算 |
| 峰值电流 | | | — | 与电源/电池放电能力匹配 |
| CPU 占用（峰值） | | | ≥30% | 留出中断与后续功能 |
| 唤醒次数 / 上报频率 | | | — | 与功耗直接耦合 |

**预算超了就砍功能或换型号，不要指望「优化代码挤出来」。**

## 二、硬件与固件版本矩阵

规划阶段就建立兼容矩阵，否则量产后会出现「新固件刷到老板子上不启动」：

| 硬件版本 | 支持的固件版本 | 差异点 | 注意事项 |
|---|---|---|---|
| HW Rev A | FW 1.0.x | 基准 | |
| HW Rev B | FW 1.0.3+ | 换了传感器型号 | 固件需运行时识别或分版本编译 |

要点：
- 硬件改版必须同步更新固件识别逻辑（可用 GPIO 配置电阻、EEPROM 版本字节）
- 固件版本号规则提前定：`主.次.修订`，主版本变更意味着协议或存储布局不兼容

## 三、通信协议先行

**先定协议，再写业务。** 协议返工是嵌入式项目最贵的返工。

规划阶段必须定：
- [ ] 帧格式：帧头、长度、命令字、负载、校验（CRC 类型与多项式）
- [ ] 字节序（大端/小端）、字段对齐、填充规则
- [ ] **协议版本字段与向后兼容策略**（新字段只能追加在末尾，旧端忽略未知字段）
- [ ] 错误码体系（设备侧 / 云端侧分别定义）
- [ ] 时序约束：应答超时、重试次数、退避策略
- [ ] 分包与重组规则（超过单帧长度时）
- [ ] 幂等设计：同一指令重复下发不能产生副作用（用指令序号去重）
- [ ] 时间同步方式（设备无 RTC 时如何定时间基准）

## 四、可靠性设计（规划阶段就要列进模块）

- [ ] **看门狗**：独立看门狗 + 喂狗点设计（只在主循环健康时喂，不可在中断里喂）
- [ ] **异常现场保留**：HardFault/异常复位时保存 PC/LR/栈快照到非易失区，重启后可导出
- [ ] **掉电保护**：关键参数写入需考虑掉电瞬间（双备份 + 校验 + 写入时序）
- [ ] **弱网与断连**：重连退避、离线缓存、上线后补传、数据去重
- [ ] **状态机兜底**：任何等待外部响应的状态都要有超时出口，禁止无限等待
- [ ] **启动自检**：外设初始化失败要有降级或明确故障指示（LED 闪烁码 / 错误码上报）

## 五、可观测性（决定后期能不能远程定位问题）

- [ ] 日志分级（ERROR/WARN/INFO/DEBUG），**编译期可裁剪**
- [ ] 量产固件默认关闭 DEBUG 级，但保留运行时开启通道（串口命令 / 云端指令）
- [ ] 关键事件打点：上电原因、复位次数、重连次数、错误码累计
- [ ] 现场问题导出：可通过串口或云端拉取最近 N 条日志与故障快照
- [ ] 设备唯一标识（SN / MAC / IMEI）在首次启动时写入并可读取

## 六、OTA 与量产（最容易在方案里被漏掉的一块）

OTA：
- [ ] 分区布局（bootloader + app + 备份区 / A-B 双分区），规划阶段就定 Flash 分配
- [ ] 传输完整性：分片校验 + 整体 MD5/SHA + 签名验证
- [ ] **断点续传与断电恢复**（下载中断不能变砖）
- [ ] **回滚机制**：新固件启动失败 N 次自动回退旧版本
- [ ] 灰度策略：按批次/白名单放量，可暂停

量产：
- [ ] 烧录方式（SWD / UART / 治具 / 脱机烧录器），单台耗时
- [ ] 产测模式：进入方式、测试项（射频、功耗、按键、LED、传感器、通信）、判定标准与记录
- [ ] 校准参数（射频、传感器零漂）写入与校验
- [ ] 序列号 / MAC / 密钥的分发与写入（避免重复）
- [ ] 出厂固件与后续 OTA 的关系（产线固件可滞后，但必须能升级到最新）

## 七、认证与合规周期（必须前置）

| 项目 | 周期量级 | 备注 |
|---|---|---|
| 无线型号核准（SRRC 等） | 月级 | 需样机，方案定案后才能送测 |
| CE / FCC | 月级 | 出口必需 |
| 电池运输认证（UN38.3 等） | 周~月级 | 带电池产品常见卡点 |
| 3C / 行业准入 | 月级 | 按品类 |

**规划时把这些周期画进时间线**，不要放在「上线前一周」。

## 八、里程碑与时间估算调整

嵌入式项目的估算不确定性显著高于纯软件，按以下方式调整：

1. **每个阶段预留 20%~30% 硬件联调缓冲**，且显式写在计划里
2. **第一个里程碑必须是「最小可运行验证板」**：一块板 + 一条完整链路（如 MCU → 模组 → Broker → 上位机）打通，功能可以极简
3. **工作量区间放宽**：给「乐观 / 现实 / 悲观」三档，而不是单一区间
4. **硬件相关步骤标注依赖**：需不需要等打样、等模组到货、等认证结果
5. **软件可在无硬件时并行的部分要单独标出**（协议层、数据解析、上位机、模拟器），这是压缩周期的关键
6. **优先做 PC 端模拟器/桩程序**：用脚本模拟设备上报，让云端与前端提前并行开发

## 九、裸机 vs RTOS 决策点（写进技术栈章节）

| 判据 | 倾向裸机前后台 | 倾向 RTOS |
|---|---|---|
| 并发逻辑数量 | < 5 个 | ≥ 5 个或有明显优先级差异 |
| 阻塞式 IO | 少，可用状态机改写 | 多（多路串口、网络、文件） |
| 时序要求 | 宽松，可容忍主循环延迟 | 有硬实时约束（如电机控制、音频） |
| RAM | 极紧张（< 8KB） | 有余量（RTOS 有栈开销） |
| 团队经验 | 无 RTOS 经验 | 有经验或有可参考项目 |
| 长期演进 | 功能基本固定 | 功能会持续增加 |

**决策要写理由，不要只写结论。** 若选裸机，需说明「如何避免主循环被单个任务拖死」（状态机拆分、非阻塞驱动、时间片轮转模拟）。

## 十、嵌入式方案自检

- [ ] 有资源预算表，各项有余量
- [ ] 有硬件/固件兼容矩阵
- [ ] 协议格式、版本字段、兼容策略已定
- [ ] 看门狗、异常现场、掉电保护已进模块清单
- [ ] 弱网/断连/超时出口已设计
- [ ] 可观测性方案（日志分级 + 远程导出）已定
- [ ] OTA 分区、回滚、断点续传已定
- [ ] 产测方案（烧录、测试项、校准、SN）已定
- [ ] 认证周期已画进时间线
- [ ] 每阶段有 20%~30% 联调缓冲
- [ ] M0 是最小可运行验证板，且链路已打通
- [ ] 无硬件时可并行的部分已识别
- [ ] 裸机/RTOS 选型有理由
