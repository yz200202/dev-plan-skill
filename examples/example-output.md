# 示例输出：净水设备小程序远程监控

> 这是一个**示例**，展示技能输出的完整结构与粒度。实际输出内容随需求变化。
> 需求：给已有的净水器加一套手机端查看滤芯状态、远程开关机、接收换芯提醒的能力，设备通过 4G 模组上行。

---

## 需求理解与假设

**一句话需求**：让用户在微信小程序里看到净水器滤芯余量和用水数据，并能远程开关机。

**核心场景**：家庭用户想知道滤芯还能用多久、漏水时能远程关机；厂家希望在滤芯到期前主动推送提醒，带动复购。

**关键约束**：团队 1 人（嵌入式背景，无前端经验）；设备侧固件已量产，改动成本高；希望 4 周内出可用版本。

**假设清单**：

| # | 假设内容 | 若不成立的影响 |
|---|---|---|
| 1 | 现有固件已能通过 MQTT 上报水质与滤芯数据 | 需增加固件改动，周期 +2 周 |
| 2 | 设备使用固定 topic 前缀，可按设备号区分 | 需改协议，影响阶段三与阶段五 |
| 3 | 小程序主体已认证，无需额外类目资质 | 上线时间不可控 |

---

## 一、可行性结论

**总体结论**：有条件可行

| 维度 | 结论 | 依据 |
|---|---|---|
| 技术可行性 | 可行 | MQTT 上行数据与指令下发均为成熟方案；设备侧仅需确认已实现的指令集 |
| 平台可行性 | 有条件 | 小程序主包体积上限以官方最新文档为准；远程控制类功能需在隐私政策中说明 |
| 资源可行性 | 有条件 | 1 人无前端经验，小程序端是最大瓶颈；建议用模板化 UI 降低学习成本 |
| 成本可行性 | 可行（千元级） | 轻量云服务器 + 域名备案 + 证书，首年千元量级 |
| 合规与法务 | 需确认 | 收集设备与用水数据，需隐私政策与最小必要说明；不涉及个人敏感信息 |

**前置条件**：

1. 确认现有固件的指令集包含「开机 / 关机 / 查询状态」，且应答有明确回执
2. 确认设备上报频率与字段，能否支撑「滤芯余量」计算
3. 域名完成备案（周期以周计，需立刻启动）

**降级路径**：若固件不支持远程控制，先只做「只读监控 + 到期提醒」，控制功能列入 P1 随下次 OTA 上线。

## 二、核心功能模块拆解

**用户旅程**：扫码绑定设备 → 查看滤芯与用水 → 收到到期提醒 → 远程关机 → 联系换芯

| 层 | 模块 | 职责 | 输入 → 输出 | 依赖 | 优先级 | 工作量 |
|---|---|---|---|---|---|---|
| 设备端 | 数据上报 | 定时上报水质、累计用水、滤芯剩余 | 传感器 → MQTT | 固件现有能力 | MVP | 0（复用） |
| 服务端 | MQTT 接入 | 订阅设备主题，解析并校验报文 | MQTT → 结构化数据 | Broker | MVP | 2~3 人日 |
| 服务端 | 设备与用户绑定 | 绑定码生成、归属关系 | 绑定码 → 绑定记录 | 数据库 | MVP | 2~3 人日 |
| 服务端 | 数据存储与查询 | 最新状态 + 历史曲线数据 | 上报 → 查询接口 | 数据库 | MVP | 2~4 人日 |
| 服务端 | 指令下发 | 下发开关机并等待回执 | 用户操作 → MQTT 指令 | MQTT 接入 | MVP | 2~3 人日 |
| 小程序 | 设备列表与详情 | 展示状态、滤芯余量、用水量 | 接口 → 页面 | 查询接口 | MVP | 4~6 人日 |
| 小程序 | 远程控制 | 开关机交互与结果反馈 | 点击 → 指令 | 指令下发 | P1 | 2~3 人日 |
| 服务端 | 到期提醒 | 定时判断滤芯余量并推送 | 定时任务 → 订阅消息 | 存储 | P1 | 2~3 人日 |
| 小程序 | 历史数据图表 | 用水趋势可视化 | 历史接口 → 图表 | 查询接口 | P2 | 3~5 人日 |

**Out of Scope（本期不做）**：

- 多设备管理与家庭共享：单人单设备先验证价值，多设备需要权限模型
- 支付与耗材商城：涉及资质与交易链路，独立立项
- 故障自诊断：需要固件上报更多诊断字段，随下次硬件迭代

## 三、技术栈推荐

**约束权重**：团队熟悉度（Node 已用）> 运维成本（单人）> 生态 > 性能 > 长期维护

| 层 | 候选 A | 候选 B |
|---|---|---|
| 小程序 | 原生小程序 ✅ 无构建链，调试直接，包体积最小 | uni-app ⚠️ 跨端能力本需求用不上，反而增加构建与排错成本 |
| 后端 | Node.js + Fastify ✅ 与现有 MQTT 桥接代码同语言，直接复用 | Spring Boot ❌ 单人维护，启动与部署复杂度不划算 |
| 数据库 | SQLite ✅ 数据量小、单机部署，零运维 | MySQL ⚠️ 需要独立进程与备份策略，当前量级无收益 |
| 消息 | MQTT Broker ✅ 设备侧已定 | WebSocket 自建 ❌ 需重做设备侧 |
| 部署 | 单台轻量云 + 反向代理 + 进程守护 ✅ | 容器编排 ❌ 单机单服务，无收益 |

**结论**：原生小程序 + Node.js(Fastify) + SQLite + 现有 MQTT Broker，单机部署。

**核心逻辑**：全链路保持一种语言（JS/TS），单人可维护；数据量在万级以内，单机单库足够。

**被否候选的否决原因**：

- uni-app：本项目只发小程序，跨端收益为零，但引入构建链与样式兼容问题
- MySQL / 容器编排：当前量级下增加的是运维负担而非能力

**反过度设计检查**：本方案未引入 Redis（状态直接查 SQLite，QPS 远低于瓶颈）、未引入消息队列（指令下发量级为个位数每分钟）。

## 四、项目目录结构

```
water-miniapp/
├── server/                     # Node.js 后端
│   ├── src/
│   │   ├── mqtt/               # Broker 连接、订阅、报文解析与校验
│   │   ├── modules/
│   │   │   ├── device/         # 设备状态、绑定关系
│   │   │   ├── command/        # 指令下发与回执等待
│   │   │   └── notify/         # 到期判断与订阅消息推送
│   │   ├── db/                 # SQLite 连接、迁移脚本、查询封装
│   │   └── http/               # 路由、鉴权、统一错误响应
│   ├── config/                 # 环境配置（Broker 地址、密钥）
│   └── tests/                  # 报文解析与指令流程单测
├── miniapp/                    # 微信小程序
│   ├── pages/
│   │   ├── index/              # 设备列表
│   │   ├── detail/             # 设备详情与滤芯状态
│   │   └── bind/               # 扫码绑定
│   ├── components/             # 状态卡片、滤芯进度环
│   ├── utils/                  # 请求封装、格式化
│   └── app.*                   # 小程序入口与全局配置
├── deploy/                     # Nginx 配置、启动脚本、备份脚本
└── docs/                       # 协议文档、接口文档
```

**组织规范**：

- 后端按 feature-first 分模块（`modules/device` 内含路由、服务、数据访问），避免分层目录里跨 5 个文件夹改一个功能
- 文件命名 kebab-case；小程序页面用目录名作页面名
- 新增一个功能：后端加 `modules/<feature>/`，小程序加 `pages/<page>/`，接口在 `http/` 注册

## 五、开发步骤

### M0 可运行骨架（3~5 人日）

- **目标**：后端能起、能连 Broker、能读库；小程序能拉到一条假数据
- **交付物**：仓库结构、配置加载、日志、健康检查接口、数据库初始化脚本、小程序首页空壳
- **验收标准**：`curl /health` 返回 200；Broker 连上后日志打印「已订阅 X/water/B/#」；小程序首页显示接口返回的假设备
- **依赖**：服务器与域名就绪

### M1 端到端最短链路（5~8 人日）

- **目标**：真实设备上报 → 入库 → 小程序看到真实数据
- **交付物**：MQTT 解析入库、查询接口、详情页展示
- **验收标准**：设备上电上报后 10 秒内，小程序详情页显示最新水质数值；设备断电 5 分钟后页面显示「离线」；非法报文被丢弃并记录告警日志
- **依赖**：M0、设备可用

### M2 功能补全（8~12 人日）

- **目标**：绑定、远程控制、到期提醒全部可用
- **交付物**：扫码绑定流程、指令下发与回执、定时提醒任务
- **验收标准**：未绑定设备不可见；下发关机后 5 秒内页面状态变为「已关闭」并显示回执时间；指令超时 10 秒给出失败提示；滤芯余量低于 10% 触发一次订阅消息且 24 小时内不重复推送
- **依赖**：M1

### M3 打磨上线（5~8 人日）

- **目标**：异常处理、隐私政策、提审上线
- **交付物**：全局错误兜底、隐私政策页、日志与告警、部署脚本与备份脚本、接口文档
- **验收标准**：断网、超时、设备离线三种场景均有明确提示；服务器重启后服务自动恢复；数据库每日自动备份且可还原验证一次
- **依赖**：M2

**关键路径**：M1 的设备联调不可并行（需真实设备）；小程序 UI 可在 M0 阶段与后端并行开发。

## 六、风险与难点

| 风险 | 类型 | 早期触发信号 | 影响 | 概率 | 应对 / 回退 |
|---|---|---|---|---|---|
| 固件指令集与文档不一致 | 技术 | 联调时下发指令无回执或回执字段缺失 | 高 | 中 | M1 阶段先做指令集实测清单；不一致则降级为只读监控 |
| 4G 弱网导致掉线丢数据 | 技术 | 联调期日均重连次数偏高 | 中 | 高 | 应用层心跳 + 指令序号幂等 + 上线补传；页面明确展示离线状态 |
| 无前端经验，小程序工期超预期 | 进度 | M0 阶段页面搭建耗时超过预估 2 倍 | 高 | 高 | 用现成 UI 模板，砍掉图表（P2）；必要时外包 UI 部分 |
| 域名备案周期不可控 | 依赖 | 提交后 5 个工作日无进展 | 高 | 中 | 先用 IP + 内网穿透联调，备案与开发并行 |
| 订阅消息模板审核不通过 | 依赖 | 首次提审被驳回 | 中 | 中 | 备选：小程序内红点提醒 + 短信（有成本） |
| 单人维护无监控，故障靠用户反馈 | 运维 | 无 | 中 | 中 | 加最小告警：进程存活 + 心跳超时推送到微信 |

**技术难点**：

1. 指令回执的可靠匹配：建议先用「指令序号 + 超时」的最小实现验证，不引入复杂状态机
2. 滤芯余量算法口径：需与硬件确认是按流量累计还是按时长估算，口径不同结果差异大

**协作难点**：固件改动需硬件同事配合，排期不受控；建议把「固件需改动的部分」集中成一次，避免多次返工。
